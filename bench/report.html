Same Markdoc, 3.5–5.7× faster at runtime

I measured the full pipeline on real Redocly content and changed only JavaScript. Output stays byte-identical. The runtime gets 1.3–1.6× faster with no API change, and 3.5–5.7× faster with three new opt-in calls. Stored ASTs shrink about 3×. Neither Rust nor a different engine is needed.

Where 0.6.4 spent its time

I profiled every stage first. The biggest costs were not in markdown parsing.

28%

Reviving stored JSON was the largest stage on pages, costing more than tokenizing the markdown. JSON.parse(text, reviver) calls back into JS for every string and number, and V8 skips its JSON fast path.

86%

of transform on API descriptions went to mergeConfig. Every call spreads about 90 tag, node and function schemas into fresh objects, even for a 34-character string.

77%

of stored AST bytes are structure. Every node repeats "$$mdtype":"Node", "attributes":{}, "children":[] and "type". Text nodes are 44% of all nodes and carry the full envelope.

  • fromJSON: plain JSON.parse, then one bottom-up walk that turns $$mdtype objects into class instances. Same result as the reviver.
  • Node.walk(): iterative instead of one nested generator per ancestor. The table transform walks every parsed document, whether or not a page has tables.
  • validate: no generator, and one parents array and config per parent instead of per node. No merged attribute schema object is built per node.
  • transform: attributes are visited in merged order without building the merged object, and the stateless built-in attribute types are instantiated once.
  • Parser and HTML renderer: no regex per token; HTML is appended into one string instead of map().join('') at every level.

Opt-in APIs

All three are backwards compatible and produce identical output. Each is opt-in because it gives up a guarantee that some caller could depend on.

Markdoc.prepareConfig(config)

Merges the built-in tags, nodes and functions once. A symbol brand survives the portal's { ...markdocOptions, ...config, variables } spread. The prepared config is reused only while tags, nodes and functions are still the same objects. Trade-off: it is a snapshot, so tags added in place afterwards are not seen.

validate: pages 1.29×, descriptions 2.41× · transform: pages 1.21×, descriptions 3.00×

prepareConfig(config, { cloneAst: false })

Transform copies only the nodes on the way to a variable or function, not the whole tree. Trade-off: a schema transform that mutates its input node would now mutate the input AST. No built-in or Redocly runtime schema does this; the portal's only node mutation is a build-time resolver that runs before storage.

pages transform with a prepared config: 155 → 121 ms (1.28× more)

Ast.pack(ast, { compact: true }) · Ast.unpack(value)

A lossless, JSON-compatible storage format. unpack(pack(ast)) serializes exactly like fromJSON(JSON.stringify(ast)), checked on every corpus document. unpack takes the parsed value and never mutates it. pack with compact: true applies compact() in the same pass: serializing a page AST drops from 158 to 99 ms.

The AST representation

Nodes become arrays recognized by position: [head, attributes?, ...children]. The head is the type, or %name for a tag, with ~ marking inline nodes. Plain inline text is just its string. Rare fields (errors, annotations, slots, location) ride under $-keys, which can't clash because attribute names are identifiers.

  • The WASM boundary costs more than Rust saves. comrak turns pages into HTML in 117 ms, but handing JS a tree it can work with takes 450 ms, the same as Markdoc's whole tokenize + parse. Validation, schema transforms and renderers are user-extensible JS, so Markdoc needs a JS tree.
  • The best Rust design would emit the packed format as a string, then JS does JSON.parse + unpack. I estimate about 230–250 ms against 392 ms today: roughly 1.6× on parsing, which is about a quarter of build time. That would mean reimplementing the tag grammar, annotations, the indentation patch, admonitions, comments, frontmatter and stopAfter with exact markdown-it compatibility. It's not worth it for that payoff.
  • Rebuilding on mdastic is the same compatibility project, for at most about 2× on the same quarter of build time. Markdoc's own plugins add about 18% on top of markdown-it core.
  • Don't upgrade markdown-it for speed: 15.0 is 1.5× slower than 12.3 on pages and 2.2× slower on descriptions.

Tried and dropped

  • A hand-written loop instead of flatMap in transformer.children was 9% slower. Reverted.
  • Rewriting the Node.resolve and base.resolve clones made no measurable difference. Reverted.
  • One-pass props in the React renderer were 0–15% slower. React rendering is bound by React.createElement itself.
  • An automatic mergeConfig cache with an exact staleness check reached only 1.4×, because checking about 90 keys costs nearly as much as copying them. The opt-in prepareConfig gets 3.0×.
  • The first A/B harness loaded both builds into one process. Whichever was required first ran about 35% faster, even when the files were byte-identical. Every build now runs in its own process, and an A/A run agrees within about 3%.

Next steps

  • Adopt the opt-in APIs in Redocly. Three changes bring most of the gain:
    • markdocRenderer.tsx: unpack(source) instead of fromJSON(JSON.stringify(source)).
    • runtime-transform.ts: prepareConfig(markdocOptions, { cloneAst: false }) once per process.
    • Storage: pack(ast, { compact: true }) behind a cache-version bump. Old JSON stays readable through fromJSON.
  • Transform straight from the packed form, skipping Nodes for subtrees without a custom transform. The measured upper bound is 108 vs 121 ms, a small gain for a lot of complexity.
  • Parallel builds with worker_threads. Pages are independent. I didn't measure this because the shared machine was too loaded for wall-clock numbers.
  • The tokenizer is now the largest build-time stage (357 ms on pages). Larger gains there need a parser rewrite.

Measured on a shared, heavily loaded machine (load average 12–57) using process CPU time and medians of interleaved rounds. Stages under 10 ms wobble by up to 8%. Raw outputs and scripts are in bench/ on the perf/explore branch; bench/REPORT.md has the long version.
