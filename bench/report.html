Markdoc's own parser

The fastest JS markdown parsers beat markdown-it mostly through their machinery, not their grammar. src/fastparse keeps Markdoc's exact grammar and replaces the machinery. The grammar is markdown-it 12.3.2's CommonMark rules with tables and strikethrough, plus Markdoc's tags, annotations, indentation rules and plugins and parser.ts's token-to-Node logic, odd cases included.

  • mdastic-style machinery: line offsets in reused typed arrays found with indexOf, pooled tokens, first-character rule dispatch, sticky regexes, and Nodes built directly with no tokens-to-AST pass.
  • No markdown-it at all. Its few helpers are vendored over the same entities, mdurl, punycode and uc.micro packages, so results match. The bundle drops from 67.5 KB to 59.4 KB gzipped.

One deliberate difference: an unclosed inline tag in link text, like [a {% t %}](/u), makes 0.6.4 throw a TypeError out of parse. The branch turns it into a node with a missing-opening error, as Markdoc does for every other unmatched close.

What's new for Redocly

parse(source, { linkify: true })

Bare www., http(s):// and ftp:// URLs and email addresses become links by GitHub's own rules (cmark-gfm's autolink extension), not linkify-it's fuzzy matching. That covers the same boundaries and domain checks, trims trailing punctuation, entities and unbalanced parentheses, and never touches links, link text, images or code. Every GFM spec autolink example is a passing unit test.

import { htmlTags } from '@redocly/markdoc/dist/html' · parse(source, { html: htmlTags() })

Your Realm HTML handler, built in and optional. Elements become html tags with React-converted attributes and the markdown between their opening and closing tags as children. Unclosed elements close after a markdoc-error tag, and invalid names stay text. It runs inside the parser, with no extra token pass, and ships as a separate entry with htmlparser2 8.0.2 bundled, so the main bundle doesn't grow.

Identical to Realm's own processHtmlTokens (bundled straight from the Redocly repo) on all 8,940 documents, 373 of them with HTML, and on 3,000 random HTML documents

Link reference definitions in linear time (markdown-it#996)

markdown-it reads every definition from its whole block, so a run of N definitions costs O(N²). The parser reads only the lines a definition needs and keeps CommonMark's rules. The three getRules('reference').length = 0 patches can go.

parseFirstHeading(source, { ...options, skip }) — replaces tokenizeUntil

Returns the first heading Node, skipping slots and any tags skip(tag) rejects, such as prompts and agents-only content. It never parses the rest of the document: it reads a growing window at the start of the source, stops at the heading, and builds only the heading. The result is always the node a full parse would give. It mirrors the builder's handling of unclosed tags, and when the heading uses a later link reference it falls back to a full parse.

First heading of all 1,129 pages: 9.1 ms, against 41.1 ms for 0.6.4's tokenizeUntil (4.5×) and 195 ms for a full parse. Identical on the corpus under 7 settings and in 60,000 fuzzed comparisons.

frontmatter: false turns off frontmatter parsing for callers that read it themselves. It's on by default, as in the original library.

parseAndValidate(source, config, args) → { ast, errors }

One call that returns the AST, with positions for error locations and future change highlighting, together with its validation errors. Validators have to see the finished tree, after the table and lone-tag transforms, so validation is still one walk at the end. Ast.pack(ast, { compact: true }) drops the positions for storage.

Opt-in runtime and storage APIs

  • prepareConfig(config) merges the built-in schemas once. That merge was 86% of transform on short descriptions. The result survives { ...prepared, variables } spreads. It's a snapshot, which is why it's opt-in.
  • { cloneAst: false } makes transform copy only the nodes that hold variables or functions. Output is identical; only a schema that mutates its input node could tell the difference.
  • Ast.pack / Ast.unpack is a lossless storage format that is still plain JSON: 10.1 MB against 29.2 MB for pages, and it decodes about 4–5× faster than 0.6.4's fromJSON. unpack takes the already-parsed value, so API docs can skip the stringify round trip.

Moving Redocly over

import { htmlTags } from '@redocly/markdoc/dist/html';
const OPTIONS = { html: htmlTags(), allowIndentation: true, allowComments: true };

// portal compiler.ts — was: Tokenizer + #996 patch + processHtmlTokens + parse(tokens)
const ast = markdoc.parse(rawContent, { ...OPTIONS, file: relativePath, slots: true });

// realm-plus parse-cache.ts
Markdoc.parse(rawSource, { ...OPTIONS, slots: true });
  1. Delete the workarounds: the three reference-rule patches and the three process-html-tokens.ts copies. Drop htmlparser2 wherever only those used it.
  2. Storage: Ast.pack(ast, { compact: true }), behind a cache-version bump. Old JSON still loads with fromJSON.
  3. Runtime: Ast.unpack(source) in markdocRenderer.tsx, and prepareConfig(markdocOptions, { cloneAst: false }) once in runtime-transform.ts.
  4. Code that reads tokens uses the removed API: realm-plus's MarkdownToken type and markdoc-editor's TokenizerInternals.

Rust and WASM

comrak, compiled from Rust to WASM, turns pages into HTML in 114 ms. Handing JS a tree costs it 454 ms, though, which is 2.5× slower than the new JS parser's 180 ms for a full Markdoc AST. Markdoc's validation, schemas and renderers are user-extensible JS, so a Rust core would only trade parsing for serialization. It's not worth it.
