I measured the full pipeline on real Redocly content and rewrote the slow parts in TypeScript: a new parser in the style of mdastic, plus a smaller AST format and a cheaper runtime path. Output stays byte-identical to 0.6.4 throughout. Neither Rust nor a different engine is needed.

Build is the noisiest number: 0.6.4's page build measured 793–965 ms across runs.

A new parser, in the style of mdastic

The fastest JS markdown parsers beat markdown-it mostly through their machinery, not their grammar. So src/fastparse keeps Markdoc's exact grammar and swaps the machinery. The grammar is markdown-it 12.3.2 with Markdoc's indentation patch, all of Markdoc's tokenizer plugins, and parser.ts's token-to-Node logic, odd cases included. It goes straight from source text to Markdoc Nodes, with no markdown-it tokens in between.

  • Line offsets live in typed arrays that are reused across documents and found with indexOf. markdown-it loops over every character to build them.
  • Pooled token objects are reused across documents, instead of a new Token() per token, and Nodes are built as tokens are consumed.
  • Rules are dispatched by first character instead of being tried in turn. Anchored regexes run sticky in place instead of on a src.slice(pos) copy.
  • Work Markdoc never reads is skipped: image labels aren't re-parsed, the table transform skips documents with no table tag, and pure URL normalization is memoized.

parse(string) uses the new parser by default. The tokenizer option takes the same settings as new Tokenizer(config), so the portal's html/allowIndentation/allowComments setup gets it too. Passing tokens still goes through markdown-it, which doubles as the escape hatch, and the Tokenizer API is unchanged. Settings the new parser doesn't implement (linkify, typographer, a non-default maxNesting) fall back to markdown-it automatically.

Costs: the bundle grows from 68 to 87 KB gzipped, since it ships both parsers. A markdown-it upgrade or a new tokenizer plugin now has to be ported too; the identity check and the fuzzer exist to catch drift.

Where 0.6.4 spent its time

28%

Reviving stored JSON was the largest stage on pages, costing more than tokenizing the markdown. JSON.parse(text, reviver) calls back into JS for every string and number, and V8 skips its JSON fast path.

86%

of transform on API descriptions went to mergeConfig. Every call spreads about 90 schemas into fresh objects, even for a 34-character string.

77%

of stored AST bytes are structure. Every node repeats "$$mdtype":"Node", "attributes":{}, "children":[] and "type". Text nodes are 44% of all nodes.

  • fromJSON: plain JSON.parse, then one bottom-up walk that revives class instances. Same result as the reviver.
  • Node.walk(): iterative instead of one nested generator per ancestor.
  • validate: no generator, one parents array and config per parent, nodes collected into flat arrays, and no per-node temporaries.
  • transform: attributes are visited without building merged objects, and the built-in attribute types are instantiated once.
  • HTML renderer: output is appended into one string instead of map().join('') at every level. React rendering is bound by React.createElement; restructuring it was slower, so it's unchanged.

Opt-in runtime APIs

Markdoc.prepareConfig(config)

Merges the built-in schemas once. A symbol brand survives the portal's { ...markdocOptions, ...config, variables } spread. The prepared config is reused only while tags, nodes and functions are still the same objects. Trade-off: it's a snapshot, so tags added in place later aren't seen.

validate: pages 1.45×, descriptions 2.99× · transform: pages 1.26×, descriptions 2.77×

prepareConfig(config, { cloneAst: false })

Transform copies only the nodes on the way to a variable or function, not the whole tree. Trade-off: a schema transform that mutates its input node would now mutate the input AST. No built-in or Redocly runtime schema does this.

Ast.pack(ast, { compact: true }) · Ast.unpack(value)

A lossless storage format that is still plain JSON. Nodes are recognized by position, and plain text is stored as a bare string. unpack never mutates its input, and pack applies compact() in the same pass.

Rust and WASM

  • The boundary eats the Rust speed. comrak turns pages into HTML in 115 ms, but handing JS a tree takes 443 ms. That's slower than the new JS parser's 176 ms for a full Markdoc AST.
  • The best Rust design would emit the packed format as a string. JS would still pay 131 ms to decode it on top of the Rust parse, which is no better than what the JS parser does now. It's not worth it.
  • Don't upgrade markdown-it for speed: 15.0 is 1.5× slower than 12.3.

Next steps

  • Adopt in Redocly.
    • Build: parse(src, { ...args, tokenizer }) instead of parse(tokenizer.tokenize(src), args).
    • Storage: pack(ast, { compact: true }) behind a cache-version bump.
    • markdocRenderer.tsx: unpack(source).
    • runtime-transform.ts: prepareConfig(markdocOptions, { cloneAst: false }) once per process.
  • Rollout. The new parser is the default for parse(string) on this branch. A more cautious release would ship it behind the tokenizer option only, for one version first.
  • Parallel builds with worker_threads. Pages are independent. I didn't measure this because the shared machine was too loaded for wall-clock numbers.
  • What's left in the build is mostly validate (about 200 ms on pages), then the parser.
